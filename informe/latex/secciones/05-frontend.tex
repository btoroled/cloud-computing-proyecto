\label{sec:frontend}
\textit{Responsable: Alexander.}

\subsection{Objetivo y arquitectura de la aplicación}
El frontend implementa un centro de operaciones del Aeropuerto Internacional
Jorge Chávez con React, TypeScript y Vite. React Router organiza la navegación;
Swagger UI integra la documentación. La aplicación separa páginas, componentes
reutilizables, tipos, clientes HTTP, adaptadores y datos simulados.
El navegador consulta APIs, sin conectarse directamente a las bases de datos
ni ejecutar consultas en Athena.

\subsection{Flujos implementados}
\subsubsection{Consulta de vuelos y manifiesto}
Operaciones incluye listado, búsqueda, filtros y detalle. Consulta también
aerolíneas para mostrar sus nombres; si esta consulta falla, mantiene el
identificador de aerolínea recibido con el vuelo.

El selector de estado presenta transiciones permitidas: Programado admite
Embarcando, Retrasado o Cancelado; Embarcando admite Despegado, Retrasado o Cancelado;
Retrasado admite Embarcando, Despegado o Cancelado; Despegado admite Aterrizado.
Aterrizado y Cancelado son finales. La validación definitiva corresponde a MS2.
En modo real, la hora de despegue se muestra a partir de la respuesta del backend.

El manifiesto consulta detalle y resumen de MS4. Sus adaptadores conservan
advertencias de dependencias y muestran como no disponibles los campos
no entregados, como determinados nombres, asientos o equipajes.
Una respuesta parcial no equivale a un manifiesto completo.

\subsubsection{Tickets y check-in}
Se cargan vuelos de MS2 y categorías migratorias de MS1. La emisión busca
al pasajero por documento, lo registra cuando no existe y solicita el ticket.
La validación del vuelo por MS1 requiere evidencia del backend para demostrar
su consumo de MS2. Tras emitir el ticket se muestra el comprobante y se habilita
el check-in. Actualmente se envía counter \texttt{WEB} y
\texttt{con\_equipaje=false}; no se implementa aquí un flujo completo de equipaje.

\subsubsection{Recursos e incidencias}
La vista lista recursos e incidencias, filtra recursos por estado y cambia
su disponibilidad. Adapta los campos de mangas y radares. Las incidencias
incluyen gravedad, descripción, tipo, recurso y, opcionalmente, vuelo.
La persistencia y validación de las asociaciones corresponden a MS3.

\subsubsection{Dashboard}
Se consultan cinco resultados de MS5: recursos con más fallas, retraso promedio
por tipo de vuelo, incidencias de combustible por aerolínea, recaudación TUUA
por categoría y vuelos retrasados en hora punta.
Las solicitudes se ejecutan en paralelo; actualmente, un fallo en cualquiera
hace fallar la carga conjunta. Los adaptadores transforman sus respuestas
para las tarjetas y gráficos. Los mocks permiten revisar la interfaz, pero
no demuestran ejecución de Athena.

\subsection{Configuración, errores y documentación}
\texttt{VITE\_API\_BASE} define API Gateway. Los mocks están activos por defecto.
Para probar todos los servicios reales se requiere
\texttt{VITE\_USE\_MOCKS=false} y \texttt{VITE\_REAL\_SERVICES} vacío.
Esta última variable permite activar servicios por etapas; una ejecución mixta
no acredita la integración completa.

El despliegue previsto en Amplify utiliza \texttt{dist} y reescritura hacia
\texttt{index.html}. Se deben verificar rutas y CORS desde el origen público.
Las variables de Vite se incorporan al compilar, por lo que cambiar la URL
requiere una nueva compilación.
\pendiente{Registrar las URLs HTTPS definitivas del frontend y API Gateway,
la versión utilizada y la fecha de prueba real.}

El cliente maneja errores 404, 409, 422 y 502--504, además de problemas de conexión
y configuración. Configura 12 segundos de espera para solicitudes habituales
y 75 para MS5. Las vistas incluyen estados de carga, vacío y error y diseño
adaptable. La revisión local debe repetirse en la versión desplegada.

En \texttt{/docs}, un selector carga los cinco contratos OpenAPI. Las URLs
se derivan de API Gateway, con sobrescritura individual; sin URL base se usan
direcciones locales. Su funcionamiento depende de la publicación y acceso
a cada especificación.

\subsection{Validación y alcance}
En la revisión del 22 de septiembre de 2026, sobre el commit \texttt{34fbd30}, se ejecutaron nuevamente
\texttt{npm test}, \texttt{npm run lint} y \texttt{npm run build}:
las cuatro pruebas de contratos pasaron, el análisis estático terminó sin errores
y se generó la compilación de producción. Vite advirtió que el paquete de
Swagger supera 500 kB; no impidió compilar y queda como oportunidad de optimización.
Estas comprobaciones no realizan una prueba de integración con AWS.

El registro \path{docs/VALIDACION_LOCAL.md} del frontend, del 21 de septiembre
de 2026, documenta compilación y análisis estático correctos, recorridos con
mocks de las cuatro vistas y revisión local del catálogo y diseño reducido.
No constituye evidencia de funcionamiento en AWS.
Las pruebas de contratos emplean respuestas de ejemplo de MS4 y MS5.
La comprobación final exige repetir recorridos sin mocks y registrar las
respuestas HTTP. La ejecución de Athena y las llamadas entre backends
deben acreditarse con sus respectivos responsables.
